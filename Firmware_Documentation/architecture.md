## 1. What the system is

A digitally controlled **analog** mixing console. The audio path is analog end to end;
the microcontroller never touches audio samples. Its entire job is to read the physical
controls — encoders, buttons, faders — and emit **control voltages** that steer the
analog cards.

One **bucket** is a 4-channel slice of the console: one STM32G474RET6 (LQFP64) driving
four electrically identical I2C buses, one per channel. Each bus carries three MCP23017
GPIO expanders (inputs) and five MCP4728 quad DACs (control voltage out). A separate
master controller — the same part — coordinates buckets; its firmware is an empty CubeMX
shell at this commit.

@note The part number is `Mcu.CPN=STM32G474RET6` in both `BucketController.ioc` and
`MasterController.ioc`, and `STM32G474RETx` in Skylar's pin diagram. Do not be misled by
`Firmware/STM32G474VET3_MX/vet6.ioc`, which is a scratch CubeMX project targeting
`STM32G484VET6` — a different part in a different package. The first draft of this page
said `STM32G474VET6`, which is neither.

## 2. Layer map

Three layers, with a strict rule that calls only go downward:

| Layer | Directory | Responsibility |
|---|---|---|
| Drivers | `Core/Src/hardware_drivers/` | Talk to one chip or one bus. Know registers, not meaning. |
| Integration | `Core/Src/control_integration/` | Turn hardware events into console meaning, and meaning back into LEDs. |
| Applications | `Core/Src/FreeRTOS_apps/` | Talk to the outside world. |

Two cross-cutting facts:

- **The drivers deliberately bypass the STM32 HAL.** `i2c_driver.c` drives the I2C
  peripheral registers directly, `74hc595.c` bit-bangs GPIO with cycle counting, and
  `led_driver.c` configures TIM1 from scratch. This is a timing decision, not a stylistic
  one — see section 4.
- **`CONFIG.h` parameterizes all three layers.** Pin assignments, clock rates, console
  geometry and bus addresses live there, split into a developer and a release block.

## 3. End-to-end data flow

### The load-bearing idea: poll to cache

I2C transactions are meant to happen **only** on a fixed schedule. Everything else reads
and writes cached bytes in RAM. `mcp23017_poll_to_cache()` performs the bus transaction;
`mcp23017_read_from_cache()` — used by `get_button_state()` and `get_encoder_motion()` —
touches no bus at all. `mcp4728_cache.c` mirrors the same pattern for the write
direction: `mcp4728_cache_write()` stores a value, and a flush pushes it out later.

This is what keeps control logic from blocking on a bus, and what makes the slot schedule
in section 4 possible. It is the single most important pattern in the codebase.

### Input path: knob turn to control voltage

Gaps are marked inline, at the point in the chain where the chain is actually broken.

1. `mcp23017_poll_to_cache(bus, addr)` — one I2C transaction, two bytes (GPIOA + GPIOB).
   *Today:* `StartDefaultTask` in `main.c` calls this for `I2C1` / `0x20` only. Expanders
   `0x21` and `0x22`, and buses `I2C2`–`I2C4`, are never polled.
2. `get_encoder_motion()` reads the cached bits and decodes quadrature into
   `ENCODER_TURN_A` / `ENCODER_TURN_B` / `ENCODER_NO_TURN`.
3. `update_channel_knob_values()` accumulates that motion into `channel_control_vals[ch]`,
   saturating at the scalar limits. `update_channel_button_values()` does the equivalent
   edge detection for buttons.
   *Today:* two knobs on channel 0 — see section 5. **← GAP: the button path is wired to
   nothing.** `update_channel_button_values()` reads `io->mute_button.button`, but
   `init_button_controls()` is an empty function body, so that `button_info_t` is never
   populated. The read is of uninitialized memory, and `update_channel_button_leds()` is
   an empty stub, so no button LED output exists either.
4. **← GAP: no CV mapping.** `control_voltage.c` has a license banner and nothing else —
   no declarations in the header, no code in the `.c`. Nothing converts a
   `channel_controls` value into a DAC count.
5. `mcp4728_cache_write(bus, addr, out_ch, val)` stores a 12-bit value.
   *Today:* never called, because step 4 does not exist.
6. **← GAP: no scheduled flush.** `mcp4728_cache_flush_fastWrite()` exists and works, but
   nothing invokes it. The slot scheduler that was meant to is not built.
7. DAC output → analog card.

### Output path: value to LED ring

1. `update_channel_knob_leds()` scales control values down to ring positions (section 6).
2. `knob_led()` / `button_led()` write into the LED framebuffer in `led_driver.c`.
3. `led_update()` shifts the whole frame out to the 74HC595 chain.
   *Today:* `StartDefaultTask` calls this every 16th loop iteration.

### Honest summary of the loop

The **input half runs end to end today**, for two knobs on one channel: turn the encoder
and the LED ring follows. The **output half stops before the DACs** — the firmware
currently cannot produce a control voltage in response to a knob, because steps 4 and 6
above are missing. Closing those two gaps is the critical path for this project.

The **button path does not run at all**, despite looking wired: see the gap marked at
step 3.

Two other paths are also unconnected: `remote_cmd_handler` acknowledges commands from the
Digilog Remote app but never writes `channel_control_vals`, and `console_state_bucket.c`
is a bare license banner that is not even listed in `CMakeLists.txt`, so nothing is
persisted across power cycles and the file is not compiled.

And per section 1.1, the entire logic-control-voltage path — the `SR3`–`SR5` shift
register outputs that switch mic/line/Hi-Z, phantom power, phase, EQ and compressor
bypass, insert routing and sidechain sends — has no software path at all. It is not a
gap in this diagram; it is a system this page does not diagram.

## 4. The I2C slot scheduler

> **Status: specified, not implemented.** `i2c_driver.c` provides only blocking
> `i2c_read()`, `i2c_write()` and `i2c_probe()`. There is no slot timer and no slot loop.
> The main loop free-runs instead. Read this section as a description of the design being
> worked toward, not of running code.

The schedule is **Skylar Denno's design**, specified in the header comment block at the
top of @ref i2c_driver.h. That comment is the authoritative statement of it. This section
adds nothing new — it only works through the arithmetic, because the numbers look
arbitrary until you do.

### Where the numbers come from

All four buses run fast-mode I2C at 400 kHz, so **one bit takes 2.5 µs**. Everything
follows from that.

| Operation | Bits on the wire | Time |
|---|---|---|
| MCP23017 2-byte read | ~29 (start, address, 2 data bytes + ACKs, stop) | **~73 µs** |
| MCP4728 fast write | ~82 (start, address, 8 data bytes + ACKs, stop) | **~210 µs** |

The expander read is only that short because of a configuration choice worth noticing:
`mcp23017_init()` sets `IOCON_SEQOP` (byte mode) and parks the address pointer at
`GPIOA`. That removes the register-select byte and the repeated start from every single
poll. The reason is the author's own, recorded in the register notes in @ref mcp23017.h —
byte mode means the same address can be read repeatedly *"w/o sending control bytes
(reduces traffic on the bus)"*.

@note Inferred: that this particular bit is what makes the 667 µs slot close is my
reading, not a documented claim. A conventional register read would cost roughly half
again as much, which would not fit the budget below.

The DAC write is 8 data bytes because a fast write carries all four output channels at
once; this matches `I2C_MAX_TRANSFER_LEN 8` in @ref CONFIG.h.

### The slot

| Step | Duration | Cumulative |
|---|---|---|
| Read MCP23017 `0x20` | 73 µs | 73 µs |
| Read MCP23017 `0x21` | 73 µs | 146 µs |
| Fast write to one DAC | 210 µs | 356 µs |
| Fast write to another DAC | 210 µs | 566 µs |
| Idle margin | 101 µs | **667 µs** |

667 µs per slot = **1.5 kHz**, which is `I2C_SLOT_PERIOD_US` in `CONFIG.h`.

### The superframe

15 slots form a superframe: 15 × 667 µs = **10 ms = 100 Hz** (`I2C_SLOTS_PER_SFRAME`).

The 15th slot spends its idle margin reading the third expander, `0x22`, which carries
only push buttons. That drops its idle time to 28 µs and gives buttons a 100 Hz poll rate
while encoders keep the full 1.5 kHz.

**Why the split matters:** EC11 quadrature encoders produce edges fast enough that a slow
poll silently drops detents, so they need the 1.5 kHz rate. Buttons are pressed by human
fingers and are perfectly well served at 100 Hz. Spending bus time proportional to how
fast each input can actually change is the entire reason for the two-tier design.

@note Inferred: the specific choice of 1.5 kHz is not justified anywhere in the source.
It may come from an EC11 maximum detent-rate figure or may have been chosen empirically.
Worth confirming with Skylar before treating it as a hard requirement.

### DAC round-robin

Only two of the five DACs are written per slot, cycling so that each is refreshed evenly:

```
 [0] 0,1   [1] 2,3   [2] 4,0   [3] 1,2   [4] 3,4
 [5] 0,1   [6] 2,3   [7] 4,0   [8] 1,2   [9] 3,4
[10] 0,1  [11] 2,3  [12] 4,0  [13] 1,2  [14] 3,4
```

30 writes per superframe ÷ 5 DACs = **6 writes per DAC per superframe**, evenly spaced
1.667 ms apart. At 100 Hz superframes that is a **600 Hz update rate per DAC** — the
"low speed 600 Hz sample rate stream" the header comment refers to.

All four buses run this schedule in parallel, one per channel.

## 5. The three struct trees in `control_integration`

This is the part of the codebase most likely to confuse a new reader: three struct trees
with nearly the same shape, describing the same 4 channels. They answer three different
questions.

| Tree | Declared in | Answers | Lifetime |
|---|---|---|---|
| `channel_controls` | `Inc/control_integration/control_interface.h` — **public** | What the console *means*: gain, mute, EQ, comp | Persisted, shared with other subsystems |
| `channel_control_io_t` | `Src/control_integration/hardware_sets.h` — **private** | Where each control physically *is*: bus, address, pin, ring index | Fixed at init; changes with PCB revisions |
| `channel_control_io_state` | `Src/control_integration/hardware_state_sets.h` — **private** | The last raw *reading*, for edge and motion detection | Transient scratch; never persisted |

### Why only the first is public

The CV engine, the remote command handler and the state-save code all need to read and
write control *values*. None of them should know that the mute button happens to be on
pin 5 of the expander at `0x22`. Keeping `channel_controls` as the only exported type
means a PCB revision that moves every pin touches exactly one module.

### How privacy is enforced

Not by convention — by the build. The private headers live under `Core/Src/`, while
`CMakeLists.txt` puts only `Core/Inc` on the include path. A file outside the module that
writes `#include "hardware_sets.h"` simply fails to resolve it. Quoted includes resolve
relative to the including file, which is why the module's own files can use the short
form while nobody else can.

### The `(vals, state, io)` convention

Every update function takes all three trees for one channel as explicit pointers:

```c
void update_channel_knob_values (channel_controls *vals,
                                 channel_control_io_state *state,
                                 channel_control_io_t *io);
```

This keeps each function pure with respect to a single channel — it cannot accidentally
read channel 0's wiring while updating channel 2, and it can be tested on a synthetic
channel without touching globals.

> **Status: partial.** The trees are fully defined, but `channel_control_io_t` is barely
> populated. `init_knob_controls()` fills in two knobs — input gain and HF EQ gain — with
> hardcoded `I2C1`, channel 0, and explicitly dummy `button_info_t` values;
> `init_button_controls()` is an empty function body, which means the mute button that
> `update_channel_button_values()` reads is **never initialized** — that read is
> undefined behaviour today, not just an unwired control. This is **bring-up scaffolding,
> not a mapping strategy**: the `channel` parameter is accepted and ignored, so all four
> channels currently describe the same physical hardware. Populating these trees from the
> pin map in @ref i2c_driver.h is outstanding work.

@note This module was reorganised twice in the week before this page was written — the
public header moved from `Inc/` into `Inc/control_integration/`, and
`rotary_encoder_control.c` was renamed `knob_control.c` when LED output was folded into
it. File names here are newer than surrounding documentation may suggest.

## 6. Scalars and scaling

`u_scalar_control_t` and `s_scalar_control_t` are **device-independent normalized
values**. They are not volts, not decibels, not DAC counts. A knob accumulates into one,
the remote protocol transports one, and the CV engine will eventually map one onto a
voltage — and none of those three has to agree with the others about units, only about
range.

At this commit both are 16-bit: `uint16_t` and `int16_t`, with `U_SCALAR_CONTROL_MAX`,
`S_SCALAR_CONTROL_MAX` and `S_SCALAR_CONTROL_MIN` defined from the corresponding limits.

@note Inferred: these narrowed from 32-bit to 16-bit two days before this page was
written. The reason is not recorded in the source or the commit message. The observable
consequence is that a 16-bit value still carries 16× more resolution than the 12-bit DACs
consume (65536 vs 4096), leaving ample headroom for smooth accumulation before
quantization, at half the storage for four `channel_controls`. **Do not read that as the
motive** — confirm with Darya.

### Encoder feel is arithmetic, not magic

In `knob_control.c`:

```c
s_scalar_control_t default_sensitivity = S_SCALAR_CONTROL_MAX / 64;   // = 511
```

511 units per detent across a ±32767 range means roughly **128 detents to sweep the full
range**, and about 256 in the fine mode you get by holding the encoder's push-button,
which halves the step. That is the knob's feel, expressed as one constant. Note that this
constant was `/16` before the width change, so the *relative* step size changed too.

### Mapping onto LED rings

`sscalar_to_8bit()` divides by `U_SCALAR_CONTROL_MAX / 33`, so across the ±32767 signed
range it yields **−16 to +16** — 33 values.

A 32-LED ring cannot show 33 positions around a center. With `CENTER_LED 15` and
`LEDS_PER_KNOB 32` from @ref CONFIG.h, `led_driver.c` derives
`CENTER_MIN = -15` and `CENTER_MAX = +16`: **32 positions, spanning −15 to +16.** The
scaler's −16 is one past the bottom of the ring.

@warning The first draft of this page asserted that −16..+16 was "exactly the 33 positions
a 32-LED ring can display," which reads as a clean fit and is wrong in both directions —
the ring has 32 positions, not 33, and they are not symmetric about the center. The same
divisor produces a worse version of this in the unsigned path: `uscalar_to_8bit()` returns
0..33, i.e. 34 values, for the same 32-LED ring. Both are open defects (items 7 and the
section 6 note in the project's follow-up list) and should be settled before anyone treats
this mapping as specified.

> **Status: least settled part of the design.** The widths changed two days before this
> page was written, the sensitivity constant changed with them, the ring mapping is off by
> one as described above, and **no consumer of these values exists yet** —
> `control_voltage.c` is a bare banner, so nothing has yet defined what a scalar means in
> volts. Treat the abstraction as agreed and the calibration as entirely open.

@note Open question for the authors: `SEND_CHANNELS` is defined as 4 in
`control_interface.h` and `CHANNELS` as 4 in `CONFIG.h`. They are numerically equal
today, which hides whether they are meant to stay independent. If a bucket ever has a
channel count different from the send count, code that conflates them will break.

heading. A status table with a stale SHA is worse than no status table, because it
invites trust it has not earned.
